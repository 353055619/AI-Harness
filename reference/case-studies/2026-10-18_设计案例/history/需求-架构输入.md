## 角色与权限

### 系统操作角色（登录用户，统一账号接入 NFR-01）

| 角色 | 目标 | 关键权限/可见范围 |
|---|---|---|
| 业务接口人（内部） | 代合作方发起并推动合作立项全流程 | 发起合作立项、填单、指定审批/评审/验收人（挂靠部门）、上传合同附件+填协议编号、验收后发起付款（FR-07/08/09/11） |
| 审批人（内部） | 完成分派到本人的审批 | 处理我的待办；合作立项单审批人由接口人发起时指定，社区激励审批人由系统配置（FR-08/13） |
| 评审人（内部） | 完成评审环节 | 合作立项由发起时指定（FR-08）；非采支付流程含评审环节（FR-16） |
| 验收人（内部） | 对项目/激励成果验收 | 合作立项验收人由发起时指定（FR-08/10）；社区激励验收支持多次（FR-14） |
| 授权签核人（内部） | 对支付单行使授权签核 | 非采支付「授权签核」环节操作者（FR-16） |
| 系统管理员（内部） | 维护平台基础配置 | 权限管理、白名单管理（导入、变更审批）（FR-03/04） |
| 社区开发者（外部·开源社区平台） | 本人发起激励申请并跟踪 | 仅能看到和处理本人的申请单（NFR-02）；仅白名单内可发起（NFR-03/FR-12） |

### 被记录对象（本期非系统操作者）

| 对象 | 说明 | 关联约束 |
|---|---|---|
| 合作方/付款对象 | 高校、科研院、组织、个人；覆盖 4 大类：开发者、高校人才、开源社区、生态伙伴 | 合作立项的合作方（1:N）、非采支付的付款对象；组织及以上须签合同、个人免（FR-09）；仅白名单内可被支付（NFR-03） |

**权限规则（GR-01，D-002；GR-03，D-027；GR-04，门1 R4 用户裁决 D-033）**：GR-01——同一张单据上评审人≠审批人、审批人≠验收人；GR-03——支付单评审/授权签核由配置池解析且不得为该单付款发起人，白名单变更审批人独立配置且≠提交人；GR-04——同一支付单上评审人≠授权签核人。管理员对不可用处理人有改派兜底（D-032）。

## 业务实体

- **电子流单据（通用）**：表单定义、流程实例、待办任务——底座三引擎的载体（FR-01）
- **工作空间条目**：我的待办 / 我的申请 / 我的已办（FR-02）
- **角色与权限配置**：内部五类角色 + 管理员、外部开发者；权限→目录/功能/动作可见性（FR-03）
- **白名单条目**：对象（开发者/组织）、导入批次（Excel）、变更审批记录（FR-04）
- **消息通知**：触发节点、接收人、已读状态（FR-05）
- **附件**：所属单据、环节、文件（FR-06）
- **合作立项单**：项目信息、合作方集合（1:N）、合同附件+协议编号+合同规定金额、验收记录（多次）、付款/核销记录（多次，GR-02）→ 派生非采支付单（FR-07~11）
- **社区激励单**：开发者（1:1）、任务/成果信息、验收记录（多次）、合并付款（一次）→ 派生非采支付单（FR-12~14）
- **非采对外支付单**：上游来源单据、付款对象（4 类）、流程状态（接收上游信息→评审→授权签核→发送统一付款平台）（FR-15/16）
- **生态合作协议服务**：迁移资产；与电子流仅协议编号引用级关联（NFR-05）

## 核心流程

| 流程 | 触发角色 | 步骤要点 | 业务规则/异常分支 |
|---|---|---|---|
| 合作立项流 | 业务接口人 | 代填发起（项目+多个合作方：均录对象标识与收款账户；组织级合同规定金额在合同待补态录入合同实体、个人级发起时录付款额度；指定审批/评审/验收人，互斥校验 GR-01）→ 评审（结论写入处理记录）→ 审批（依据结论，意见/驳回理由留痕，D-003）→ 合同信息齐备（金额进验收中即锁定）→ 验收（多次，结论通过/不通过，可标记验收完结）→ 选定合作方付款（按其额度核销 GR-02），生成非采支付单；额度核销尽+无在途支付单→完结（退回冲回触发回退 D-029），或接口人手动完结·无在途支付单（剩余额度作废留痕 D-031）；撤回→草稿可编辑重提可换人；处理人不可用时管理员改派兜底（D-032） | 项目:合作方=1:N（FR-07）；组织须签合同、个人免（FR-09）；多次验收多次付款（FR-10/11）；付款前置=≥1条通过验收（D-014） |
| 社区激励流 | 社区开发者本人 | 发起（任务/成果+成果附件，白名单会话身份校验，仅 开源社区平台）→ 池绑定审批人审批（确认/下调通过金额）→ 池绑定验收人多次验收（≠审批人 GR-01，可标完结）→ 完结标记后审批人合并一次付款（额度=审批通过金额 GR-02）→ 生成非采支付单；待审批可撤回（D-021） | 项目:开发者=1:1（FR-13）；非白名单拦截并附指引（NFR-03/FR-12）；付款发起人不得任本单支付评审/授权签核（GR-03） |
| 非采对外支付流 | 上游流程生成 | 生成支付单（对象/收款账户/金额/付款依据）→ 接收确认（可拒收 D-022）→ 评审 → 授权签核 → 发送统一付款平台（目标态呈现）；评审/授权签核由配置池解析且≠付款发起人（GR-03）；拒收/评审退回→已退回+核销冲回+通知上游（激励流同步开发者），重发引用原支付单（D-010） | 不独立发起（FR-15）；固定四步、授权签核必备（FR-16）；本期无统一付款平台系统对接（NFR-04）；上游发起人只读跟踪派生支付单 |
| 白名单管理流 | 系统管理员 | Excel 导入（整单校验 D-016）/手工变更 → 变更单提交审批（审批人池指定，≠提交人 GR-03）→ 通过后按审批时间串行写回 | 变更未经审批不生效（FR-04）；匹配键=统一账号ID/统一社会信用代码（D-015） |
| 权限管理流 | 系统管理员 | 配置角色（一人可多角色）与五类人员池（激励审批/激励验收/支付评审/支付授权签核/白名单审批；保存校验池非空、激励审批/验收池无交集）→ 决定可见性与解析；配置变更留痕 | 覆盖内部五类角色+管理员、外部开发者（FR-03）；流程定义本期开发预置、只读查看（D-026） |
| 底座公共流 | 全部角色 | 待办产生与处理、申请/已办记录、消息通知触达、附件挂接 | 通用引擎支撑三流，新流可快速接入（FR-01/02/05/06，NFR-06） |

## 约束与非功能需求

| 编号 | 约束 |
|---|---|
| NFR-01 | 接入示例企业生态统一账号（生态发展项目账号），不自建账号与登录 |
| NFR-02 | 外部用户仅能看到和处理本人的申请单（列表/详情/操作均限本人） |
| NFR-03 | 白名单为支付资格硬约束：仅白名单内开发者/组织可被发起激励或支付 |
| NFR-04 | 统一付款平台本期无系统级对接；支付单审批走至终点，界面按目标态呈现「已向统一付款平台提交付款申请」 |
| NFR-05 | 生态合作协议服务仅迁移运营、不做新功能、不连通其他应用服务；电子流仅协议编号引用级关联 |
| NFR-06 | 表单/流程/待办为通用底座，后续新电子流可快速接入 |
| NFR-07 | 界面按三级目录：我的工作空间 / 对外支付项目（合作项目框架、合作项目、非采对外支付）/ 系统管理 |
| GR-01 | 权限互斥：同一单据上评审人≠审批人、审批人≠验收人，指定/配置时校验（D-002） |
| GR-02 | 付款额度管控：设核销阶段，每次付款留记录，累计付款不得超过额度上限——立项按合作方（组织=合同规定金额、个人=付款额度 D-009），激励=审批通过金额（D-006/D-009） |
| GR-03 | 权责分离：支付单评审/授权签核由配置池解析且≠付款发起人；白名单变更审批人独立配置且≠提交人（门1 R1，D-027） |
| GR-04 | 支付单同单权责互斥：评审≠授权签核（门1 R4 用户裁决，D-033） |

**范围 Out**（防蔓延，架构不为其设计）：统一付款平台系统对接、协议服务新功能、连通其他应用服务、自建账号、开源社区平台 外激励渠道。
