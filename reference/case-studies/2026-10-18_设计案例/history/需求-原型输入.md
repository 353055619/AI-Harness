# 需求·原型输入

> 派生自 原始需求.md（+已裁决 GR 增量），只分解不发明；可随迭代修订。当前无 GR 增量（首轮分解）。用户类别与 需求-架构输入.md 角色清单同源；命名以 术语.md 为准。

## 用户类别

| 用户类别 | 是谁 | 来做什么 | 成功长什么样 |
|---|---|---|---|
| 业务接口人 | 示例企业内部合作接口人 | 代合作方发起合作立项、补合同、发起付款 | 单据从发起走到付款，全程在我的申请可查 |
| 审批人 | 示例企业内部（合作立项由发起时指定；激励由系统配置） | 处理我的待办中的审批 | 待办处理后状态正确流转 |
| 评审人 | 示例企业内部 | 完成评审环节（合作立项/非采支付） | 评审意见留痕、流转继续 |
| 验收人 | 示例企业内部（合作立项发起时指定） | 执行验收（支持多次） | 每次验收记录可查 |
| 授权签核人 | 示例企业内部 | 对支付单授权签核 | 授权签核后支付单走向「发送统一付款平台」 |
| 系统管理员 | 示例企业内部平台管理员 | 维护权限与白名单 | 权限生效；白名单导入与变更审批可用 |
| 社区开发者 | 开源社区平台 社区开发者（外部） | 本人发起激励、跟踪本人单据 | 仅见本人申请单（NFR-02）；非白名单者发起被拦截 |

> 合作方/付款对象（高校、科研院、组织、个人；4 大类）本期为被记录对象，不作为原型可操作角色。

## 关键旅程

| 旅程 | 用户类别 | 步骤串（入口→操作→反馈→去向） | 关联 |
|---|---|---|---|
| J1 发起合作立项 | 业务接口人 | 对外支付项目>合作项目 → 发起 → 填项目信息+多个合作方+从挂靠部门指定审批/评审/验收人（同一人兼任互斥角色时拦截，GR-01）→ 提交 → 「已提交」提示 → 我的申请出现该单（评审中） | FR-07/08、GR-01 |
| J2 补合同 | 业务接口人 | 我的申请/单据详情 → 对组织级合作方上传合同附件+填协议编号（个人合作方免）→ 保存 → 合同信息区更新 | FR-09 |
| J3 评审与审批 | 评审人 → 审批人 | 我的待办 → 评审人先出评审结论（状态流转）→ 审批人依据结论通过/驳回（两人不得为同一人，GR-01）→ 待办消失、状态变更、发起人收到通知 | FR-02/08、D-003、GR-01 |
| J4 多次验收 | 验收人 | 我的待办 → 单据详情 → 录入验收结果与材料 → 完成 → 验收记录列表+1（可再次验收） | FR-10 |
| J5 发起付款（合作立项） | 业务接口人 | ≥1条通过验收后 → 立项详情发起付款 → 选定合作方（组织/个人），页面显示该合作方额度/已核销/剩余，超限拦截（GR-02）→ 生成非采支付单+核销记录 → 非采对外支付列表出现新单（本人只读可跟踪） | FR-11、GR-02、GR-03 |
| J6 发起激励 | 社区开发者 | 登录（外部视角）→ 发起激励 → 填任务/成果 → 提交 → 白名单校验通过则进入审批，否则拦截提示 | FR-12/NFR-03 |
| J7 激励验收与合并付款 | 验收人/审批人 | 验收人（池绑定，≠审批人 GR-01）多次验收并勾选「验收完结」→ 完结标记解锁审批人合并付款（额度=审批通过金额，超限拦截 GR-02）→ 生成非采支付单；开发者只读跟踪支付进度 | FR-14、GR-01、GR-02、D-013 |
| J8 支付单处理 | 评审人/授权签核人 | 我的待办 → 支付详情（含付款依据）→ 接收确认（可拒收→已退回·核销冲回·通知上游 D-022/D-010）→ 评审 → 授权签核 → 终态「已向统一付款平台提交付款申请」；授权签核不通过退回评审 | FR-16、NFR-04、GR-03 |
| J8a 支付退回重发 | 业务接口人/审批人 | 收到退回通知（含原因）→ 立项/激励详情重新发起付款（额度已释放）→ 新支付单引用原单 | D-010 |
| J8b 白名单变更审批 | 审批人 | 我的待办 → 白名单变更单详情（≠提交人 GR-03）→ 通过→串行写回生效 / 驳回→理由留痕 | FR-04、GR-03 |
| J8c 撤回与重提 | 业务接口人/社区开发者 | 立项评审中/审批中撤回→草稿编辑重提（可换人重跑互斥）；激励待审批撤回 | D-011、D-021 |
| J8d 处理人更换 | 业务接口人 | 立项详情对未开始环节更换评审/审批/验收人→互斥校验+通知新人 | D-023 |
| J9 权限与人员池配置 | 系统管理员 | 系统管理>权限管理 → 配置角色权限与五类人员池（保存校验池非空/激励审批验收池无交集）→ 生效+留痕 | FR-03、GR-03、D-020 |
| J10 白名单管理 | 系统管理员 | 系统管理>白名单管理 → Excel 导入（整单校验）/手工变更 → 变更提交审批（审批人池）→ 通过后串行写回生效 | FR-04、D-016 |
| J11 工作空间日常 | 全部 | 我的工作空间：待办/申请/已办三个列表（条目含单据类型/环节/到达时间）→ 点击进入对应单据 | FR-02 |

## 交互预期

- **角色切换可见性**：原型支持内部/外部视角切换；外部开发者仅见本人申请单+派生支付单只读，且目录仅 我的工作空间+社区开发者激励（D-017）；管理员可见系统管理目录（NFR-07）。
- **状态真实流转**：提交后待办真的+1；评审→审批顺序流转（D-003），结论/意见写入处理记录；验收多次追加并可标完结；完结标记解锁合并付款；付款按所选合作方核销、支付列表新增单据；退回→核销冲回+额度释放，重发生成新单引用原单；支付四步停在「已向统一付款平台提交」终态（NFR-04，无真实对接）。
- **模拟数据覆盖**：三流各状态单据；白名单内/外开发者（拦截+指引）；组织/个人合作方两态表单；4 类付款对象；接近/超额度付款样例；已退回→重发链样例；互斥冲突与池校验失败样例；变更单三状态与提交人≠审批人演示。
- **合同规则演示**：合作方类型切换（组织/个人）时合同区/额度区显隐（FR-09/D-009）；合同金额进验收中锁定（D-019）。
- **校验演示**：互斥拦截（GR-01）、付款人≠支付评审/授权签核（GR-03）、超额度拦截（GR-02）、验收完结前合并付款不可用（D-013）、付款幂等（重复点击只生成一张）。
