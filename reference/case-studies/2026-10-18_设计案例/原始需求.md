# 原始需求 · 生态运营管理

- 版本 v1 · 2026-10-18 · formalize 定稿
- 溯源：.agents/GOAL.md（已消费，源文件删除）

## 1 背景与问题

示例企业的生态建设长期分散在各产品线——终端、芯片、ICT 各自建立生态，大量工作重复、效率低下。为此示例企业启动 **生态发展项目**，统一建设示例企业生态产品；产品由多个子产品构成，可概括为全生命周期运营模型+ 生态官网 + 数智运营平台。整个项目服务于 4 大用户对象：**开发者、高校人才、开源社区、生态伙伴（企业、组织）**。

本设计对象是生态运营子产品（生态运营与演进）下的 **生态运营管理** 应用模块，职责是管理整个生态项目的**电子流**。IT 上该模块挂在数智运营平台（支撑全生命周期运营模型的运营管理平台）下作为一级菜单。

模块当前仅有一项已有资产——生态合作协议服务（线上合同签署平台），其余均处于规划阶段。本期建设（11 月 20 日上线版本）的内容是：**3 条电子流（合作立项、社区开发者激励、非采对外支付）+ 公共平台基础**。业务链条：合作立项、社区开发者激励是上游业务流，非采对外支付是下游发钱流。

## 2 用户与对象

| 用户/对象 | 是谁 | 来达成什么 | 成功长什么样 |
|---|---|---|---|
| 示例企业内部·业务接口人 | 示例企业内部负责生态合作的员工 | 代外部合作方发起合作立项、填写单据、跟进全流程 | 在系统内完成发起、指定审批/评审/验收人、上传合同附件并填协议编号 |
| 示例企业内部·审批人/评审人/验收人 | 合作立项中由接口人发起时指定（挂靠部门）；社区激励审批人由系统配置 | 在我的待办中完成各自环节的审批、评审、验收 | 待办及时可见，处理记录留痕 |
| 示例企业内部·授权签核人 | 非采对外支付流程中的授权签核环节操作者 | 对支付单行使授权签核 | 支付单经授权签核后走向「发送统一付款平台」 |
| 示例企业内部·系统管理员 | 平台管理人员 | 维护权限与白名单 | 权限配置生效；白名单可导入、变更走审批 |
| 外部·社区开发者 | 开源社区平台 社区开发者（本期唯一渠道） | 本人发起激励申请、查看和处理本人单据 | 登录后可见并可操作本人申请单，仅限本人 |
| 外部·合作方/付款对象 | 高校、科研院、组织、个人等生态伙伴；最终覆盖开发者、高校人才、开源社区、生态伙伴 4 类 | 作为合作立项的合作方、非采对外支付的付款对象被系统记录 | 合作与付款单据中对象信息准确、白名单内方可被支付 |

## 3 交付边界

本期为**设计阶段**，交付形式：4A 架构文档（markdown + C4 图，含机器可读衔接块）+ 可交互低保真 HTML 原型（JSON 模拟数据、页面跳转、状态流转）。

### 3.1 本期做什么（In）

1. **三条电子流**（FR-07 ~ FR-16）：合作立项、社区开发者激励、非采对外支付。
2. **公共平台基础**（FR-01 ~ FR-06）：电子流通用底座、我的工作空间、系统管理（权限、白名单）、消息通知、附件管理。
3. **生态合作协议服务迁移运营**（NFR-05）：仅从老服务器迁移至自有服务器运营，不做新功能。

### 3.2 本期明确不做（Out）

1. 统一付款平台系统级对接（本期打不通，界面按目标态呈现即可）。
2. 生态合作协议服务的新功能开发。
3. 与其他应用服务的连通。
4. 自建账号体系（统一接入示例企业生态账号）。
5. 开源社区平台 以外的社区开发者激励渠道。

## 4 功能需求（FR-xx）

| 编号 | 需求陈述（触发者/步骤要点/业务规则） | 关联用户 |
|---|---|---|
| FR-01 | 电子流通用底座：平台提供表单、流程、待办三个通用引擎，支撑三条电子流的定义与运转；后续新电子流可基于底座快速接入 | 全部内部用户 |
| FR-02 | 我的工作空间：每个登录用户拥有个人工作空间，含「我的待办」（需本人处理的任务）、「我的申请」（本人发起的单据及状态）、「我的已办」（本人处理完毕的记录）；从待办可进入单据处理 | 全部用户（内部+外部） |
| FR-03 | 权限管理：系统管理员维护角色与权限（内部角色：接口人/审批人/评审人/验收人/管理员；外部角色：开发者等）；权限决定目录可见性、功能可见性与可执行动作 | 系统管理员 |
| FR-04 | 白名单管理：维护支付资格白名单（开发者/组织）；支持 Excel 批量导入；白名单变更（新增/修改/删除）本身需走审批，审批通过方生效 | 系统管理员 |
| FR-05 | 消息通知：平台在电子流关键节点（待办产生、单据状态变化、处理结果）向相关用户发送通知，用户可在平台内查看 | 全部用户 |
| FR-06 | 附件管理：平台提供附件上传、查看、下载能力；电子流各环节（合同附件、验收材料等）挂接附件 | 全部用户 |
| FR-07 | 合作立项·发起：示例企业内部业务接口人**代**外部合作方填单发起（外部合作方不自行发起）；填写项目信息与合作方信息，提交后进入审批流转。规则：一个项目可关联多个合作方（项目:合作方 = 1:N） | 内部接口人 |
| FR-08 | 合作立项·人员指定：接口人在发起时从挂靠部门指定本单的审批人、评审人、验收人；后续流转按此指定执行 | 内部接口人 |
| FR-09 | 合作立项·合同：合作方为组织及以上级别须签合同，为个人则免合同；合同在线下或生态合作协议平台（老服务器）签署；电子流内上传合同附件并填写协议编号建立关联（仅「协议编号引用」级） | 内部接口人 |
| FR-10 | 合作立项·验收：由发起时指定的验收人对项目验收，同一单支持**多次验收**；每次验收记录结果与材料 | 验收人、内部接口人 |
| FR-11 | 合作立项·付款：验收后可发起付款，支持**多次验收、多次付款**；付款不直接在本流完成，流转生成非采对外支付单进入下游 | 内部接口人、审批人 |
| FR-12 | 社区开发者激励·发起：社区开发者**本人**发起激励申请（本期仅限 开源社区平台 社区开发者，如领取揭榜任务后申请）；填写任务/成果信息，提交进入审批。规则：仅白名单内开发者可被发起激励 | 外部社区开发者 |
| FR-13 | 社区开发者激励·审批：审批人由系统配置（非发起人指定）；一个激励申请对应一名开发者（项目:开发者 = 1:1） | 内部审批人 |
| FR-14 | 社区开发者激励·验收与付款：支持多次验收；多次验收**合并为一次付款**；付款流转生成非采对外支付单 | 验收人、内部审批人、社区开发者 |
| FR-15 | 非采对外支付·生成：不独立发起，由上游电子流（合作立项、社区开发者激励）流转生成支付单，携带上游信息（付款对象、金额、依据）；面向开发者、高校人才、开源社区、生态伙伴 4 类对象付款 | 系统（上游流程触发） |
| FR-16 | 非采对外支付·处理：流程固定为 接收上游信息 → 评审 → 授权签核 → 发送统一付款平台；授权签核为必备环节；到终点时界面按目标态呈现「已向统一付款平台提交付款申请」 | 评审人、授权签核人（内部） |

## 5 非功能约束（NFR-xx）

| 编号 | 约束陈述 |
|---|---|
| NFR-01 | 账号：接入示例企业生态统一账号体系（生态发展项目账号），不自建账号与登录；内部与外部用户均以统一账号进入 |
| NFR-02 | 数据边界：外部用户登录后仅能看到和处理本人的申请单（列表、详情、操作均限本人单据） |
| NFR-03 | 支付资格：仅白名单内的开发者/组织可被发起激励或支付，资格校验为硬约束 |
| NFR-04 | 统一付款平台集成边界：本期与统一付款平台无系统级对接（需统一付款平台部门会议评审通过方可打通）；支付单在系统内审批走至终点，界面按目标态呈现「已向统一付款平台提交付款申请」 |
| NFR-05 | 协议服务边界：生态合作协议服务仅从老服务器迁移至自有服务器运营；不做新功能；不与生态运营管理其他应用服务连通；与电子流仅「协议编号引用」级关联 |
| NFR-06 | 底座通用性：表单/流程/待办引擎为通用底座，后续新增电子流可快速接入，不为每条流重写基础能力 |
| NFR-07 | 界面信息架构：按三级目录组织——我的工作空间 / 对外支付项目（合作项目框架、合作项目、非采对外支付）/ 系统管理 |

## 6 已有资产与集成边界

| 资产/外部系统 | 目标态 | 本期实际 | 允许的关联方式 |
|---|---|---|---|
| 生态合作协议服务 | 生态合作协议签署平台 | 仅从老服务器迁移至自有服务器运营，无新功能 | 电子流内上传合同附件 + 填协议编号，仅「编号引用」级关联，不连通服务 |
| 统一付款平台 | 系统对接，付款单直达 | 对接打不通（需统一付款平台部门会议评审通过） | 无系统对接；界面按目标态呈现「已向统一付款平台提交」 |
| 示例企业生态统一账号 | 全平台统一身份 | 直接接入使用 | 不自建，仅接入 |
| 开源社区平台 | 社区开发者来源之一 | 本期唯一激励发起渠道 | 身份/来源标记，不做深度集成 |
