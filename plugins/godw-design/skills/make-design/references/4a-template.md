## 6 机器可读衔接块（handoff）

文档唯一供程序消费的部分，**原型段只读这里**。合法 JSON（入文前用 `jq .` 或 `node -e "JSON.parse(...)"` 验过），结构与页面/原型实现逐字对齐：

```handoff
{
  "roles": [
    { "name": "申请人", "scope": "本人单据", "permissions": ["requisition:create", "requisition:withdraw"] }
  ],
  "pages": [
    { "id": "requisition-create", "title": "发起申请", "roles": ["申请人"], "actions": ["提交", "存草稿"], "nav": "工作台 > 发起申请" }
  ],
  "entities": [
    { "name": "申请单", "fields": ["id", "applicant", "amount", "status"], "states": ["草稿", "审批中", "已通过", "已驳回"] }
  ],
  "flows": [
    { "name": "发起申请", "actor": "申请人", "steps": ["填表", "提交", "进入审批中", "审批人待办+1"] }
  ],
  "seedData": [
    { "entity": "申请单", "note": "覆盖各状态各角色各一条，供原型模拟数据库" }
  ]
}
```

字段规范：

- `roles[].permissions` 用 `<资源>:<动作>` 小写连串；`scope` 写可见范围（行级）。
- `pages[].id` 即原型页面路由名；`actions` 只列改变状态的动作用户，纯浏览不列。
- `entities[].states` 数组顺序 = 状态机主链顺序；异常分支在 flows 或 2.4 表达。
- `seedData` 说明原型模拟数据集必须覆盖的维度（角色×状态×边界值）。

## 模板使用纪律

1. **章节不增不删**（Deployment/场景走查两处标注「按需」的除外），次序不变；4A 的价值就在骨架稳定可预期。
2. **每节内容可溯源**：角色/流程/约束来自 GOAL-4A，文档不自创业务事实；确实需要但上游没有的，回 make-design 段0 的缺口机制，不硬编。
3. **两类读者自检**：写完通读一遍问自己——某角色读者能否只看本文档走完他的流程？接手开发者能否不问人就列出模块/接口/表？答不上来的地方就是门1 会打的洞，先自己补。
4. 图与表格、衔接块三者的一致性（角色对齐、状态对齐、页面对齐）是硬要求，改任一处同步其余两处。
