# 设计流水线 → ARCH-4A.md + 可交互原型（双门验收，全链进化）

## 输入（强制）

- `.agents/GOAL.md` 必须已定稿（不存在 → 先调 **godw-goal:clarify-goal** 澄清收口，再回到本流程；本技能不代办澄清）。
- 本流程启动即视为无人值守授权：GOAL.md 定稿就是目标契约，全程不再问用户，歧义当场裁决并记录。

## 产物根目录：.agents/design/（懒创建）

```
.agents/design/
├── ARCH-4A.md          4A 架构文档（架构段产物，随门反馈同步修订）
├── prototype/          原型段产物（brief / wireframe / prototype / 模拟数据）
├── gate-arch-N.md      门1 第 N 轮验收报告
├── gate-proto-N.md     门2 第 N 轮验收报告
└── DECISIONS.md        裁决记录（每条：时间/歧义/裁决/一句理由）
```

## 需求回流协议（贯穿两门的进化机制）

模拟用户走查的价值不只是找文档 bug——**真实用户会提前暴露需求本身没安排的合理诉求（gaps）**。gaps 的处理不是记下来收口再说，而是当场回流：

1. **判边界**：gap 是否超出交付边界？交付边界 = GOAL.md 第二章「澄清目标」定义的范围。判据：gap 服务于已定义的用户达成已定义的目标 → 在界内；引入新用户群/新产品方向/新价值主张 → 越界。
2. **界内 → 回写**（三级同步）：
   - `GOAL-4A.md` / `GOAL-UX.md`：必改（它们是活文档，本来就是为迭代修订而设）；
   - `GOAL.md` 第二章：**仅当 gap 改变澄清目标本体**（如目标口径、交付形式、约束）才受控修订——修订必留痕：GOAL.md 首次被修订时追加「第三章 演进记录」，逐条记（轮次/来源角色/原句→新句/一句理由）；**第一章原始目标原话永不改**（它是历史与边界的锚点）；
   - `ARCH-4A.md`：需求变了文档必跟（含衔接块），同步完再重验当前门。
3. **越界 → 停止呈报**：范围蔓延不是迭代能解决的，把越界 gaps 原话呈报用户裁决（采纳=用户手动扩大边界后重跑，拒绝=记 DECISIONS.md 后从修订清单剔除）。

这套受控修订与 clarify-goal「一次定稿」铁律不冲突：clarify-goal 守的是访谈收口后不许随手改；本协议是唯一带纪律的修订通道（门反馈驱动、边界守护、全程留痕）。

## 流程五段

### 段0 准备：双腿分解

- `GOAL-4A.md` 或 `GOAL-UX.md` 缺失或与 GOAL.md 明显脱节 → 调同插件 **split-goal** 重建两腿。
- 两腿「待澄清」小节非空时：逐条判断——能按业界默认安全裁决的（如「未提响应式→默认桌面优先自适应」）记入 DECISIONS.md 后放行；**影响成败的硬缺口**（如角色权限模型完全没说）直接停止流水线，把缺口清单呈报用户，不替用户编需求。（注：流水线启动后再发现的缺口走上方需求回流协议，不再停线。）

### 段1 架构：GOAL.md + GOAL-4A.md → ARCH-4A.md

1. 严格按 [references/4a-template.md](references/4a-template.md)（4A 四节骨架）撰写，全文存 `.agents/design/ARCH-4A.md`。
2. **图语言用 C4（Mermaid C4 语法）**，方法学按同插件 vendored **c4-architecture** 整装执行：Context 与 Container 必出，Component / Deployment / Dynamic 按 GOAL-4A 复杂度裁剪（「Context + Container 对多数团队已足够」）。图落位：Context→业务架构节、Container→应用架构节、数据模型→数据架构节（信息架构）、Deployment→技术架构节、Dynamic→场景走查节。
3. **质量铁律（纯 LLM 直出图不成熟）**：每张 Mermaid C4 图对照 c4-architecture 的语法表与 common-mistakes 自查一遍（元素三要素齐全、单向箭头、动词标注、≤20 元素）再入文。
4. **机器可读衔接块**（文档→原型不断链的关键）：按模板第 6 节规范，把角色权限矩阵、页面清单、实体与状态机、核心流程落成合法 JSON（用 `jq .` 或 `node -e` 验过再入文）。原型段**只消费衔接块**，不重新读全文理解业务。
5. 架构质量自查（对应门1 架构师维度，先自己过一遍）：业务目标逐条有支撑、扩展性/耦合内聚/性能/冗余/抽象/复用无明显反例——门1 会被专门审视，先补后验。

### 段2 门1·文字层：design-gate（doc 模式）

- 调同插件 **design-gate** 模式 `doc`：分类用户思维业务流走查 + 开发者只凭文档复现 + 架构师七维审视（角色三源并集全覆盖，含管理员/运维等生态角色）。
- FAIL → 按其三轨修订清单执行：blockers 修 ARCH-4A.md；**gaps 走上方需求回流协议**；suggestions 择优。修完重验（全新子智能体）。**安全上限 5 轮**，PASS 即收敛；超限停止呈报（附各轮报告路径、未收敛原因分析——通常是需求自相矛盾或边界争议，需要用户裁决）。
- 过门不冻结：后续门2 反馈若打到文档，文档照改（见段4），两门期间 ARCH-4A.md 始终是活的。

### 段3 原型：衔接块 + GOAL-UX.md → 可交互原型

1. **写 brief**（`prototype/brief.md`）：旅程→页面清单（与衔接块 pages 对齐）→ 页面×角色可见性矩阵（工作台/电子流类系统必须先过 **godw-html:workbench-conventions** 的审批四区/RBAC 分区惯例）→ 模拟数据方案（JSON 数据集覆盖各角色各状态）。
2. **生成**（委托 godw-html lo-fi 线，按其 make-html 的 lo-fi 分流）：
   - 结构未定 → 先 **html-wireframe** 出 2-3 个结构方向（低保真纪律，不追求像成品）；
   - 定稿 → **html-prototype** 出可交互交付 `prototype/prototype.html`：**这不是静态页**——JSON/localStorage 模拟数据库、页面跳转全通、状态流转真实发生（提交后待办列表真的多一条）、角色切换可见性随 RBAC 矩阵变化、反馈与过渡效果齐全，接近最终交付形态。
3. 原型自检：衔接块 pages 全部落页、flows 每步可操作走通、实体状态机全状态可达。

### 段4 门2·低保真层：design-gate（prototype 模式）· 文档同步修订

- 调 **design-gate** 模式 `prototype`（分类用户子智能体在原型上实操走旅程，含管理员/运维管理面）。
- FAIL → **修改低保真时同步修改文档**（用户明确要求，不必吝惜 token）：原型问题根源在哪层就改哪层——纯实现问题改原型；设计问题改 ARCH-4A.md（含衔接块、图、表同步）；需求问题走回流协议改 GOAL 系。三层改完重验（全新子智能体）。**安全上限 5 轮**，PASS 即「用户都满意、改无可改」。
- 每轮修订在三处留痕：gate 报告修订清单、DECISIONS.md（有裁决时）、GOAL.md 演进记录（有需求回流时）。

### 段5 收口：汇报

- 两门各轮成绩（通过轮次/分数曲线）、产物路径（ARCH-4A.md / prototype/ / 验收报告）、DECISIONS.md 裁决清单、GOAL.md 演进记录（如有）、遗留事项。
- 后续动作（如「拿着图纸开发」「出高保真」）由调用方决定。

## 无人值守纪律（贯穿全程）

1. **不问用户**：GOAL.md 定稿即授权；一切歧义当场裁决，每条记 DECISIONS.md（歧义/裁决/一句理由），收口时如实汇报。
2. **迭代即常态**：两门的设计目的就是让产物在被放行前先被「虚拟用户、虚拟开发者、虚拟架构师」打死几轮——这是提前预演生产版本运维，宁可门内多改几轮，不让问题漏到下一段。token 消耗不是优先级，质量收敛才是。
3. **超限即停**：任一门 5 轮不收敛，说明存在流水线内解决不了的问题（需求自相矛盾、边界争议、缺口过大），停止并呈报，不带病放行。
4. **完成即停**：两门全过即收口，不擅自扩展（不主动出高保真、不写真实后端代码）。

## 边界

- 只管「设计流水线怎么走、质量门怎么守」。`.agents/GOAL.md` 的定稿归 godw-goal 域（本协议的受控修订通道是唯一例外）；GOAL-4A/GOAL-UX 由本插件 split-goal 派生维护；HTML 制作方法学（设计纪律/实现选型/单文件构建）归 godw-html；本技能不重复它们的内容，只做衔接与守门。
- 依赖按名调用的插件（须已安装启用）：godw-goal（仅 clarify-goal 前置）、godw-html。
