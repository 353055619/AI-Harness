# 设计工件验收门 → gate 报告 + 分类修订清单

## 输入（强制）

- 模式：`doc`（验收架构文档）或 `prototype`（验收可交互原型）。
- 被验收工件路径；`doc` 模式另需 `.agents/GOAL.md` 与 `.agents/GOAL-UX.md`（或工件内 handoff.roles）作角色与目标来源。
- 输出报告路径（调用方指定，如 `.agents/design/gate-arch-1.md`）。

## 角色派生（全覆盖，三源并集）

**用户类型必须覆盖全面**——漏一个角色就等于上线后该用户第一批发现问题。三源取并集：

1. GOAL-UX.md「用户类别」逐类（业务用户）；
2. 工件内 handoff.roles 逐个（文档实际定义的角色，与源 1 有出入时以文档为准并记入报告）；
3. **系统生态角色补全**：管理员、运维、审计/合规（涉数据留痕时）、外部集成方（涉对接时）——凡该系统现实中必然存在的，一律补派，不因需求文档没提而缺席。

**每类一个子智能体**；超过 10 类才合并同类项（合并必须注明「谁并入了谁」）。doc 模式另加派两个专业角色（见下）。

## 子智能体任务书（照抄改尖括号，不加引导语）

### A. 分类用户 · doc 模式（思维业务流走查）

> 你是「<角色>」。你的目标：<该角色在 GOAL 中的原话目标>。
> 这是一份系统架构文档：<工件绝对路径>。文档描述的系统还没有做出来，你用**思维业务流**验收它：通读文档，然后在想象中把你的每一个业务流程完整执行一遍——<该角色相关流程清单>。每执行一步问自己：我能找到入口吗？系统让我做这一步吗？做完了系统怎么反馈我？出错了怎么办？
> 你是一个真实而挑剔的用户：用不上、看不懂、文档没写、前后矛盾、系统不支持你合理诉求的地方，都要吐槽出来。特别区分两类：**文档自身的缺陷**（写了但矛盾/含糊/漏了该写的）与**需求本身的缺口**（你的合理诉求在整份文档里都没被安排，因为最初没人想到——这类更要报，你是替未来真实用户在提前发现问题）。
> 只输出以下 JSON（不要其他文字）：
> {"role":"<角色>","scores":[{"flow":"<流程名>","score":<0-10>,"blockers":["<文档缺陷：看不懂/矛盾/缺失的具体位置和问题>"],"gaps":["<需求缺口：文档没安排的合理诉求，写明为什么合理>"],"suggestions":["<不阻断但值得改的建议>"]}]}

### B. 开发者复现 · doc 模式（只凭文档）

> 你是刚接手本项目的开发工程师，只拿到一份架构文档：<工件绝对路径>。不许读仓库里其他任何文件。
> 请照单复现：1) 列出你会建的模块/服务清单；2) 每个核心接口的方法/路径/入参/出参；3) 每张数据表的字段与关系；4) 关键流程的实现时序要点。
> 凡是文档没讲清、你只能猜的地方，逐条记入 blockers（注明你猜了什么、为什么拿不准）。这是对文档的考试，不是对你的——暴露文档缺口就是你的贡献。
> 只输出以下 JSON（不要其他文字）：
> {"role":"开发者(复现)","scores":[{"flow":"<按功能划分的复现区，如 接口设计/数据建模/流程实现>","score":<0-10>,"blockers":["…"],"gaps":[],"suggestions":["…"]}]}

（注：编排层发给它的任务书**不含 GOAL.md**——复现考试测的是文档自足性。回收评分后，编排层自己比对 GOAL.md 功能清单：文档没覆盖的功能直接追加为 blocker。）

### D. 架构师审视 · doc 模式（质量七维）

> 你是资深软件架构师，评审这份架构文档：<工件绝对路径>（业务目标背景：<GOAL.md 第二章一句话>）。
> 逐维评审，每个维度找具体反例（指出文档哪一处损害了该维度），没有反例才给高分：
> 1) **业务目标达成**：每条业务流程都有架构支撑吗，有过度设计吗；2) **扩展性**：加一类用户/一种单据/一个渠道要动几处；3) **耦合与内聚**：模块间是否只在边界依赖、单模块是否单一职责；4) **性能**：高频流程路径上有无结构性瓶颈；5) **冗余**：有无重复承载同一职责的模块/数据；6) **抽象**：该泛化的地方泛化了吗，还是复制粘贴式展开；7) **复用**：公共能力沉淀了吗。
> 每个维度一个 score；发现的问题按「文档缺陷 blockers / 需求缺口 gaps（架构层面没人安排的事）/ 建议 suggestions」归类。
> 只输出以下 JSON（不要其他文字）：
> {"role":"架构师","scores":[{"flow":"<七个维度逐个作为 flow 名>","score":<0-10>,"blockers":["…"],"gaps":["…"],"suggestions":["…"]}]}

### C. 分类用户 · prototype 模式（实操原型）

> 你是「<角色>」。你的目标：<该角色在 GOAL 中的原话目标>。
> 这是可交互原型：<prototype.html 绝对路径>（单文件，含全部页面/数据/跳转逻辑）。以<角色>身份实操你的每段旅程：<该角色相关旅程清单>。逐步验证：入口找得到吗？操作后有真实反馈吗？状态真的变了吗（如提交后待办列表是否多一条）？跳转到的下一页对吗？你能看到/不能看到的东西符合你的身份吗？
> 你是真实而挑剔的用户，把不好用的地方都吐槽出来；同样区分**原型做错了**（blockers）、**整个设计就没安排这个合理诉求**（gaps）、**可以更好**（suggestions）。管理员/运维角色走管理面与运维面旅程（用户管理/配置/日志/异常处理），没有对应页面本身就是一个 gap。
> 可用浏览器打开实操；无法实操时精读 HTML/JS 推演每条交互路径后作答，并在 suggestions 注明「推演非实操」。
> 只输出以上 JSON 格式（同模式 A）。

## 汇总与判定（编排层自己做，不派子智能体）

1. **并行派发**（Agent 工具一次多任务书），子智能体之间互不知晓、任务书零引导（不暗示「应该没问题」、不透露上轮分数）。
2. 收齐后逐份解析，按角色×流程汇总成表；JSON 不合法的子智能体返工重跑一次。
3. **判定线**：所有 scores[].score ≥ 8 且 blockers 总数 = 0 且 gaps 总数 = 0 → **PASS**；否则 **FAIL**。
4. **修订清单按去向分三轨**（给下一轮修订的输入）：
   - **blockers（工件缺陷）**：修订被验收工件本身，按位置去重合并；
   - **gaps（需求缺口）**：交编排层走需求回流协议（make-design 定义：判交付边界 → 回写 GOAL 系文件 → 同步工件）；
   - **suggestions（建议）**：按「影响多数角色/根治性」择优吸收，不收的在报告记一句理由。
5. 写报告（调用方指定路径），格式：

```markdown
# 门验收报告：<工件名> · 第 N 轮（<模式>）
- 判定：PASS / FAIL（判定线：全部 ≥8 且 blockers=0 且 gaps=0）
- 派发：<N 个角色子智能体（doc 模式另含 开发者复现 + 架构师审视）>（角色并集来源：GOAL-UX ∪ handoff.roles ∪ 生态补全）
## 评分汇总
| 角色 | 流程 | 分 | 阻断 | 缺口 |
|---|---|---|---|---|
## 子智能体原话（全文照录，未删改）
## 修订清单
- blockers（修工件）：…
- gaps（走需求回流）：…
- suggestions（择优）：…（未收录的注明）
## 下一步
PASS → 放行下一段 / FAIL → 修订后重验（安全上限剩余 <M> 轮）
```

## 纪律

- **独立**：子智能体并行、互不可见；同轮内不因某个低分提前终止其他走查。
- **无引导**：任务书模板照抄，只在尖括号处填空；不在任务书里替工件辩护或解释。
- **照录**：子智能体原话全文进报告，编排层不删改不润色——验收报告是证据，不是宣传材料。
- **迭代即运维**：本技能的本质是提前模拟真实用户做生产版本运维——吐槽、需求、建议都是可修改项；宁可门内多打死几轮，不让问题漏到下一段。
- **收敛与上限**：调用方约束安全上限（make-design 为每门 5 轮）；PASS 即收敛停，上限防震荡；每轮报告独立成文件，不覆盖。
- **独立性边界**：修订工件与回写需求的人可以看修订清单，但**重验必须重新派发全新子智能体**，不带记忆、不看上轮报告。
