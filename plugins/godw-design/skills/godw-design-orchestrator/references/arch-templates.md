# 四架构文档模板（业务/信息/应用/技术 + detail.json）

文档链：实例 `原始需求.md` → **本四文档（4A架构/，含 model.c4 模型源）** → `PRD/` → `原型系统/`。四文档独立成文、各答一问；字段级明细（角色权限矩阵/页面清单/接口清单/实体字段/状态机）**只存在于 `4A架构/detail.json`**——正文放叙述、图与理由（双写残留是首轮实测确认的失败模式，此铁律不可破）。每篇头部：`版本 vN · YYYY-MM-DD · 一行变更摘要`；术语以实例 `术语.md` 为准。

图统一用 Mermaid，按 **godw-toolkit:design-doc-mermaid** 的分诊与规范生成；**系统级上下文图与容器图不手写**——由 `4A架构/model.c4`（LikeC4 模型源）生成：`likec4 validate` 过 → `likec4 gen mermaid` 嵌入正文 → 人看视图 `likec4 export png` / `likec4 serve`；**模型变更后必须重新生成嵌入**（check 的 gen 防漂移规则会重跑 gen 比对，漂移即打回）。手写图（时序/流程/ER/状态）**不依赖 mmdc**——由 `godw-design-check --phase document` 做源码级校验：图型合法、引号配对、时序图参与者 ∈ 角色∪系统名、页面流转图节点 ∈ detail pages、时序图分叉块 ≤2、状态图节点 ⊆ detail entities[].states；报错回喂重修后再入文（Text→Mermaid 是实测最难格式，不过校验不入文）。

**每图一问（配图分工铁律）**：谁跟谁怎么接力=时序图（人↔系统，业务架构§3）；系统内怎么路由=flowchart（应用架构§4）；系统↔系统怎么接力=时序图（应用架构§3/技术架构§4）；数据长什么样怎么关联=erDiagram（信息架构§1）；单据怎么流转=状态图（信息架构§2）；页面怎么走=页面流转图（应用架构§2）；边界内外有谁、怎么切分=model.c4 生成图（业务架构§5/应用架构§1）；部署视图=model.c4 部署场景或手写（技术架构§2，需要时）。一种图只在一处承担一问，两处都要答案=双写。LikeC4 易错点（实测）：**元素 id 必须 ASCII**（字母开头，中文写进标题引号——`actor applicant "申请人"`）；自由文本必须加引号（`title "中文"`）；`include *` 只在 `view of <元素>` 作用域视图合法，无作用域视图显式列元素；**gen mermaid 不 gate 有效性**——必须先 validate 再 gen。

四文档的服务对象：分类用户（走查流程是否被支持）、开发者复现官（照图复现）、架构评审官（七维）、简洁审查官（反膨胀）。成文时删掉所有 `<…>` 指引。

# 业务架构.md

**回答：这个系统为谁、支撑哪些业务、规则是什么。**

- 版本 vN · YYYY-MM-DD · 变更摘要
- 目标来源：原始需求.md 摘要一句（关联 FR 见节标题标注）

## 1 业务目标与边界 [FR-xx]

<系统要达成什么（业务目标一段话）；本期范围内/外一句话各列（与原始需求 In/Out 对齐，不复制清单）；怎么算做成——可量化的成功度量（如「审批时长从 X 降到 Y」）。看板/报表类页面的口径源头在此；成功度量缺失时停笔回补需求，不编数字。>

## 2 用户与角色 [FR-xx]

<用户/角色分层的叙述：每类用户是谁、来达成什么、可见范围与权限要点（字段级矩阵在 detail.json roles，不在此复制）>

## 3 业务域、用例与核心流程

### 3.0 用例总览（一张表，带 UC 编号与 FR 挂接——check 机器核对覆盖）

<| 用例 ID | 业务域 | 用例（动词+对象） | 参与角色 | 所属流程 §3.x | 关联 FR |>——全貌一眼：哪些角色用哪些能力、归哪个域。**机器门禁三查**：每条 FR 至少被 1 个用例挂接（uc-fr-coverage）；原始需求 §2 每个角色至少 1 个用例（uc-role-coverage）；用例挂的 §3.x 流程节必须真实存在（uc-flow-ref）。每个用例必须能在某条 3.x 流程的步骤中找到（语义级）；身份卡考题在本表找不到对应用例 = 设计漏了用户目标。

### 3.1 每角色用例视图（每角色一图，节点=该角色的用例全集）

每个原始需求 §2 角色一个小节（`#### <角色名>`，角色名与 §2 逐字一致），配一张 Mermaid graph 用例图——节点 ID 用 UC-xx、与 §3.0 表中该角色的用例集合**完全一致**（uc-diagram-consistency 机器核对：图多一个节点、少一个节点都打回）；图给人看角色视角全貌，机器只认 §3.0 表。示例：

```mermaid
flowchart LR
    UC-01["UC-01 发起申请"]
    UC-03["UC-03 撤回申请"]
    UC-01 --> UC-03
```

每流程一小节（清单=需求-架构输入.md 核心流程 + 已吸收 GR，不增不减）：

### 3.x <流程名> [FR-xx]
- 触发：<角色，从哪进入>
- 步骤：<编号步骤串，每步「谁 对什么 做什么 → 系统反馈/状态变化」>
- 业务规则：<限额、审批规则、时限等硬规则，逐条 BR-xx 编号（供 PRD 引用；check 核对每个含业务规则的流程小节必有 BR 编号）>
- 异常分支：<驳回/撤回/超时/冲正时系统与各方怎么办——全在文字，不堆进图>
- 配图：Mermaid **时序图（固定）**——只画主路径 + 最多 2 个关键分叉；参与者必须用 §2 角色名与本文件 §5 系统名（对不上名字=缺陷，check 可查）

## 4 业务实体总览 [FR-xx]

<每实体一句话：业务含义、归属业务域、谁拥有（业务归属）。**状态怎么流转不在此写**——全归 信息架构§2 状态模型（防双写）；字段级模型在 detail.json entities。>

## 5 系统上下文（由 model.c4 生成，必出）[FR-xx]

<图由 `likec4 gen mermaid` 从 `4A架构/model.c4` 生成后嵌入（系统边界内外：角色 actor、外部系统、数据流向）——**不手写**；模型变更必须重新生成。人看导出图：`likec4 export png`；交互站：`likec4 serve`。>

## 6 风险与开放问题

<风险、技术债、未决事项集中落点（吸收 arc42 §11）——每条：风险/影响/缓解或决策建议；服务收口呈报。>

# 4A架构/detail.json（机器可读衔接契约，独立文件）

四文档唯一的字段级事实源，**原型生产（2a）只读这里**。合法 JSON（入盘前 `jq .` 或 node 验过；机械校验由 godw-design-check 执行）：

```json
{
  "_version": "v3",
  "_updated": "2026-10-18",
  "roles": [
    { "name": "申请人", "scope": "本人单据", "permissions": ["requisition:create", "requisition:withdraw"] }
  ],
  "pages": [
    { "id": "requisition-create", "title": "发起申请", "roles": ["申请人"], "actions": ["提交", "存草稿"], "nav": "工作台 > 发起申请", "trace": ["FR-01"] }
  ],
  "entities": [
    { "name": "申请单", "fields": ["id", "applicant", "amount", "status"], "states": ["草稿", "审批中", "已通过", "已驳回"], "trace": ["FR-01"] }
  ],
  "flows": [
    { "name": "发起申请", "actor": "申请人", "steps": ["填表", "提交", "进入审批中", "审批人待办+1"], "trace": ["FR-01"] }
  ],
  "seedData": [
    { "entity": "申请单", "note": "覆盖各状态各角色各一条，供原型模拟数据库" }
  ]
}
```

字段规范：

- `roles[].permissions` 用 `<资源>:<动作>` 小写连串；`scope` 写可见范围（行级）。
- `pages[].id` 即原型页面路由名；`actions` 只列改变状态的动作用户，纯浏览不列。
- `entities[].states` 数组顺序 = 状态机主链顺序。
- **每个元素带 `trace`**：指向 FR/NFR（原始需求）或 GR（评审裁决增量）ID 数组；确实无需求出处且属结构性种子的标 `"deferred"`——无 trace 无标记会被 godw-design-check 报「疑似发明」。
- `seedData` 说明原型模拟数据集必须覆盖的维度（角色×状态×边界值）。

## 模板使用纪律

1. **四文档职责不越界**：内容模型归信息架构、划分与接口归应用架构、选型部署集成归技术架构、用户流程规则归业务架构；跨文档引用写文件名+节号（如「见 信息架构§2.付款计划状态机」）不复制内容。
2. **字段级明细唯一源 = detail.json**：正文出现与 detail 同构的字段级表 = 模板违规（验收会被抓）；正文表格只做叙述性汇总。
3. **每节内容可溯源**：角色/流程/约束来自需求-架构输入.md（其源头是原始需求+已裁决 GR），文档不自创业务事实；缺的走 godw-design-orchestrator 需求回流协议，不硬编。
4. **节标题挂 FR 标注**：每节标题后挂 `[FR-xx]`（或 NFR/GR），与需求追踪.md 交叉核对——文档标注 ⊆ 追踪表登记（防漏登）。
5. **四类读者自检**：身份卡里的每个角色，能否只看业务架构.md 把分给他的考题答到「能做」（核心流程答卷卡住=0）？开发者能否凭四文档+detail.json 不问人列出模块/接口/表？架构师能否找到每个耦合点的理由与不变量？简洁官能否快速定位膨胀区？答不上来的地方就是门1 会打的洞。
6. 图、正文、detail.json、需求追踪.md 四者一致性（角色对齐、状态对齐、页面对齐）是硬要求；修订时**先改 detail.json 再改正文再更新追踪表**，每轮修订后跑 godw-design-check。
