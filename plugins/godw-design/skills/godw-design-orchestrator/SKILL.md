# 设计流水线编排器 → 三阶段：原始需求 → 4A架构 → 原型系统（双门验收，全链进化）

## 输入（强制）

- 需求来源两条固定路径（不做多来源探测）：
  - **路径一（首次）**：`.agents/GOAL.md` 存在（clarify-goal 已定稿）→ 阶段一调同插件 **godw-design-requirement-formalize** 转写为实例的 `原始需求.md` + `术语.md`（用户提供的参考资料原样归位实例 `参考资料/`，登记账由 1a 建账）；
  - **路径二（重测）**：`design/archive/`（优先）或 `design/change/` 下存在同设计名的上一轮实例 → 复制其 `原始需求.md` 进新实例为起点（原始需求冻结，每轮等价）。
  - 都不存在 → 先调 **godw-goal:clarify-goal** 澄清收口再回来；本技能不代办澄清。
- 自阶段一结束（用户确认原始需求冻结）起即无人值守授权：原始需求.md 就是目标契约，全程不再问用户，歧义当场裁决并记录（收口时如实汇报）。

## 三阶段与自动识别（每次调用先做）

用户感知三阶段，内部步骤 1a…2c 保留为阶段内推进粒度：

| 阶段 | 用户产物 | 内部步骤 |
|---|---|---|
| **一 · 原始需求** | 原始需求.md（冻结）+ 术语.md + 参考资料/ 归位 | 前置 formalize（**人在环：确认定稿才冻结**） |
| **二 · 4A架构** | 4A架构/ 四文档 + detail.json + 需求追踪.md + **身份卡.md** | 1a 备料（两腿+身份卡+考题+INDEX 建账）→ 1b 成文 → 1c 门1 |
| **三 · 原型系统** | 原型系统/ 可交互原型 + 收口报告 | 2a 生产 → 2b 门2 → 2c 收口归档 |

**自动识别规则**（按目录实况判断，不靠会话记忆）：

1. **实例定位**：`design/change/` 唯一实例自动选定；多实例并存 → 停下问用户选哪个；无实例 → 阶段一开工（含实例命名确认，人在环）。
2. **步骤定位按产物存在性**：无 `原始需求.md` 或未确认冻结 → 阶段一；无 `4A架构/detail.json` → 1a/1b；有 detail 而无 `history/snapshots/gate1-pass/` → 1c；有 gate1 快照而无 `原型系统/` 成品 → 2a；无 `history/snapshots/gate2-pass/` → 2b；两快照齐 → 2c（已归档则报告完成态）。
3. **state.md 对账**：启动时读实例根 `state.md` 与目录实况比对，不一致**以目录为准**并顺手修正 state.md——面板给人看，目录是唯一真相。
4. **冻结门不自动跨**：阶段一结束=用户确认原始需求定稿，编排器只能停线等候，不替用户冻结；其余阶段末出阶段报告（衔接卡片）停，放行权归调用方。
5. **推进粒度**：识别后从当前步骤连跑到**本阶段末尾**停；调用方指定只跑某步时照办（分段可独立重跑，文档修订后重跑 1c 重新验收天然支持）。

### state.md（实例根进度面板，给人看）

编排器每推进一步即更新：

```markdown
# state · <设计名>
- 当前阶段：<二 · 4A架构>
- 当前步骤：<1b · 四文档成文>
- 上一步：<1a 备料完成（两腿+身份卡+考题+INDEX；待澄清 N 条、已裁决 M 条）>
- 下一步：<1b 按 references/arch-templates.md 成文>
- 等你做什么：<无 ｜ 确认原始需求冻结 ｜ 对待澄清表态>
- 更新于：<YYYY-MM-DD HH:mm>
```

## 执行粒度与启动三档

默认连跑一次收口；也支持分段——因自动识别，**续跑 prompt 可简化为一句**（如「/goal 继续执行 godw-design-orchestrator」或「继续 godw-design 实例 <名>」，编排器自行定位当前阶段）；多实例并存须指明实例名。三档语义保留：

| 档 | 覆盖步骤 | 启动方式 | 理由 |
|---|---|---|---|
| **start** | 阶段一 formalize + 1a 需求分解 | 📋 普通粘贴 | 人在环：实例名确认、完备性关卡、待澄清表态、冻结确认 |
| **document** | 1b 四文档 + 1c 门1 验收循环 | 🤖 **必须 /goal 启动** | 成文+迭代到收敛是连续自主任务，goal 完成审计是无人值守载体 |
| **prototype** | 2a 原型 + 2b 门2 + 2c 收口归档 | 🤖 **必须 /goal 启动** | 同上，且含最终归档动作 |

## 阶段衔接规范（每步结束必须输出）

任一步（前置/1a/1b/1c/2a/2b/2c）执行完停下时，**必须**在汇报末尾输出结构化「下一步」卡片——交接可复制，任何会话任何人照卡片粘贴即可继续：

```markdown
## 下一步
- **阶段**：<如下一步，如 1b · 四文档成文>
- **调用技能**：<godw-design-orchestrator（按其执行粒度只跑 document 档）>
- **启动方式**：<🤖 /goal 前缀粘贴（document/prototype 档）｜📋 普通粘贴（start 档）> + 一句为什么
- **输入产物**：<本步产出中下一步要读的文件清单>
- **预期输出**：<下一步产物清单>
- **启动 prompt**：<可直接复制的完整 prompt 代码块（含 /goal 前缀与否）>
- **你的检查点**：<放行前应人工检查什么（如两腿待澄清是否已表态）>
```

## 产物根目录：design/（懒创建）

```
项目根/design/
├── change/                              # 进行中的设计
│   └── {YYYY-MM-DD}_{设计名}/           # 日期=创建日期；三大块=流水线三阶段
│       ├── state.md                     # 进度面板（编排器每步更新；启动对账以目录为准）
│       ├── 原始需求.md                   # 需求本体（两章；FR-xx/NFR-xx 逐条编号；冻结）
│       ├── 术语.md                       # 全链术语表（formalize 首建，随评审增补留痕）
│       ├── 身份卡.md                     # 1a 产出即冻结：身份卡组+考题六类+身份×题矩阵（gate 角色/考题唯一来源）
│       ├── 参考资料/                     # 外部资料原样落位 + INDEX.md 登记账 + archive/（已内化归档）
│       ├── 需求追踪.md                   # 中心纽带：一行一需求承载链（FR/NFR/GR）
│       ├── 4A架构/
│       │   ├── 业务架构.md / 信息架构.md / 应用架构.md / 技术架构.md
│       │   └── detail.json              # 字段级明细唯一事实源（机读）
│       ├── 原型系统/
│       │   ├── brief.md / wireframe.html(可选) / prototype.html
│       └── history/                     # 全部过程文档
│           ├── 需求-架构输入.md / 需求-原型输入.md   # 两腿（活文档）
│           ├── gate-registry.md          # 问题收敛登记表（判定基准）
│           ├── gate-arch-N.md / gate-proto-N.md     # 两门各轮报告
│           ├── snapshots/gate1-pass/、gate2-pass/   # 过门快照
│           └── DECISIONS.md              # 裁决留痕
└── archive/                              # 已完成的设计（同结构快照，日期保持创建日期）
```

文档链即交付链：**原始需求 → 身份卡/两腿 → 4A架构 → 原型系统**；术语/追踪表/身份卡/参考资料登记账是贯穿性全局工件；两腿、登记表、gate 报告、DECISIONS 是过程工件。

## 需求回流协议 v2（原始需求冻结后的进化机制）

模拟用户走查暴露的需求缺口（gaps）不当 bug 记录，当场分流：

1. **判边界**：交付边界 = 原始需求.md 的「交付边界（In/Out）」清单。gap 服务于已定义用户达成已定义目标 → 界内；引入新用户群/新方向/新价值主张 → 越界。
2. **界内 → 两腿吸收**：需求-架构输入 / 需求-原型输入是「设计侧需求工作视图」（原始需求分解 + 已裁决增量的并集），吸收必须记 DECISIONS.md 出处（轮次/来源角色/裁决理由），并给增量编 **GR-xx**（gate requirement）入追踪表；**原始需求.md 永不改**（agent 无修改权，用户改=手动带外）。参考资料内化（INDEX 待内化项中明确的业务规则）同走本通道。
3. **越界 → 停止呈报**：范围蔓延不是迭代能解决的，把越界 gaps 原话呈报用户裁决。
4. **收口呈报「建议并入原始需求的 gap 清单」**：用户认可的高价值裁决手动并入原始需求.md（带外）——下一轮重测自然继承，避免重复发现重复裁决。

## 版本系统

- 四文档每篇头部 `版本 vN · YYYY-MM-DD · 一行变更摘要`（N 对齐所在门轮次）；detail.json 顶层 `_version` / `_updated`。
- 版本日志 = history/ 各轮 gate 报告（记录每轮改了什么），不另建 changelog。
- **过门快照**：1c PASS 时快照四文档 + detail.json + **需求追踪.md** 到 `history/snapshots/gate1-pass/`（追踪表是一致性基线；2b 同理 gate2-pass/）；中间轮不存（防膨胀）。

## 流程

### 阶段一（人在环）：需求定稿

1. 路径一：调同插件 **godw-design-requirement-formalize**（输入 `.agents/GOAL.md`，输出实例 `原始需求.md` + `术语.md`，FR/NFR 编号；其完备性关卡不过则停线补澄清）。
2. 实例命名：建目录前 agent 根据需求提议设计名、请用户首肯；目录 `{YYYY-MM-DD}_{设计名}` 落 `design/change/`（子目录懒创建）。
3. 重测（路径二）时：`design/change/` 下已有**同设计名的未完成旧轮** → 停下提示用户处置（继续旧轮/人工删除/确认并存）后再建新实例。
4. **阶段末尾=冻结门**：原始需求.md 定稿须用户确认，确认前不放行（全流水线唯一人在环门）。

### 阶段二 4A架构

**1a 备料**：调同插件 **godw-design-requirement-split**——原始需求.md 定向拆解为两腿（`history/需求-架构输入.md` + `需求-原型输入.md`）+ **产出实例根 `身份卡.md`**（身份卡组+考题六类+身份×题矩阵，只从原始需求派生、产出即冻结，先于 1b——出题的人不看答案）+ **参考资料建账 `参考资料/INDEX.md`**（有资料才建账，RF-xx 逐份登记，后续内化走回流协议）。两腿「待澄清」非空时：能按业界默认安全裁决的记 DECISIONS.md 放行；影响成败的硬缺口停止呈报（流水线启动后再发现的缺口走回流协议，不再停线）。

**1b 成文**：读 `原始需求.md` + `history/需求-架构输入.md`：
1. 严格按 [references/arch-templates.md](references/arch-templates.md) 撰写 `4A架构/` 四文档 + `detail.json`（字段级明细唯一事实源，正文同构字段表=模板违规）。
2. **先建 `需求追踪.md` 骨架**（从原始需求抄 FR/NFR 清单），成文过程逐条挂链（业务架构节 | 应用架构节 | detail 元素 | 原型页面〔架构期可「待原型」〕）；四文档节标题挂 `[FR-xx]` 标注。
3. 图统一走 **godw-toolkit:design-doc-mermaid**（按名调用）；系统级 Context/Container/Deployment 用 C4 语法，对照同插件 vendored **c4-architecture** 的语法表与反模式自查；**每图一问**（配图分工见模板头部，参与者/节点名须与角色、系统、pages 清单对得上）。
4. 架构质量自查（对应架构评审官七维，先自己过一遍再送审）。

**1c 门1·文字层**：调同插件 **godw-design-gate** 模式 `doc`（动态用户评委按冻结身份卡+考题以**答卷表**验收〔能做/卡住/靠猜〕+ 开发者复现官 + 架构评审官 + 简洁审查官；探索期→收敛期两段节奏）。

- **修订循环**：FAIL → 按三轨清单修订（blockers 修工件；界内 gaps 走回流协议两腿吸收+GR 编号；suggestions 择优）→ 修订纪律：先改 detail.json 再改正文、按追踪表受影响行同步、涉术语同步术语.md、**每次替换/编辑后必须 grep 复核命中结果再继续**（二轮实测三次静默 no-op 教训，锚点漂移即停手重定位）→ **调同插件 godw-design-check 校验（不过打回修订，不耗评委轮次）** → 过 → 重验（回归+新鲜评委）。**安全上限 5 轮**，PASS 即收敛存快照；超限停止呈报。
- 过门不冻结：2b 反馈若打到架构文档照改（见 2b 门间联动）。

### 阶段三 原型系统

**2a 生产**：读 `4A架构/detail.json`（**只消费它，不重读四文档**）+ `history/需求-原型输入.md`：
1. **写 brief**（`原型系统/brief.md`）：旅程→页面清单（与 detail.json pages 对齐）→ 页面×角色可见性矩阵（工作台/电子流类**必先过 godw-html:workbench-conventions** 定分区）→ 模拟数据方案（按 detail seedData 覆盖角色×状态×边界值）。
2. **生成**（委托 godw-html lo-fi 线，按其 make-html 的 lo-fi 分流）：结构未定先 **html-wireframe** 出 2-3 方向；定稿走 **html-prototype** 出可交互交付——**默认多文件组织**：`原型系统/` 下 `index.html`（壳+路由+账号切换）+ `pages/`（每页一个模块）+ `data.js`（JSON 模拟数据库）+ `assets/`（公共样式脚本）；页面 ≥6 或业务复杂**必须**多文件（二轮实测：16 页单文件 83.5KB 导致修订锚点漂移误伤），≤5 页小场景可单文件 prototype.html。无论组织形态：**不是静态页**——模拟库跳转全通、状态真实流转（提交后待办真的多一条）、角色切换可见性随矩阵变化；data.js 独立使评委与 godw-design-check 可直接读模拟数据。
3. **填追踪表**：2a 完成后需求追踪.md 原型页面列全部填满（不再允许「待原型」）。
4. 原型自检：detail pages 全落页、flows 每步可走通、状态机全状态可达。

**2b 门2·原型层**：调 **godw-design-gate** 模式 `prototype`（动态用户评委按冻结身份卡+考题**实操原型**，含管理员/运维管理面）。FAIL → **修改低保真同步修改文档**（不必吝惜 token），问题根源在哪层改哪层：纯实现改原型；设计问题改 4A架构（先 detail 后正文）；需求问题走回流。**门间联动**：动了 `4A架构/` 则该轮 **godw-design-check 必跑** + 回归评委任务书附「受影响 FR/GR 链架构一致性」附带验证；**仅当改动触及核心不变量或边界规则时回炉 1c 重验**（防门1↔门2 死循环）。安全上限 5 轮，PASS 存快照 gate2-pass/。

**2c 收口**：汇报 + 自动归档：
- 两门各轮成绩（登记表收敛曲线）、产物路径（原始需求 / 身份卡 / 术语 / 需求追踪 / 4A架构 / 原型系统 / 验收报告）、DECISIONS 裁决清单、**backlog 呈报**（未裁决长尾交用户定夺）、**「建议并入原始需求的 gap 清单」呈报**（用户手动采纳）、**参考资料未内化项呈报**（INDEX 待内化清单）、遗留事项。
- **自动归档**：实例从 `design/change/` 挪 `design/archive/`（创建日期不变）；超限停线/悬置/废弃的**不归档**，留 change 由用户人工处置。

## 无人值守纪律（贯穿全程）

1. **不问用户**：原始需求定稿即授权（阶段一冻结门除外——那是全流水线唯一人在环点）；歧义当场裁决记 DECISIONS.md，收口如实汇报。
2. **迭代即常态**：两门是提前预演生产版本运维——宁可门内多打死几轮，不让问题漏到下一段。但**收敛≠零问题**：登记表清零即收敛，长尾进 backlog，不为清空 backlog 无限加料（简洁是质量维度）。
3. **超限即停**：任一门 5 轮不收敛 → 停止呈报（多为需求矛盾/边界争议），不带病放行。
4. **完成即停**：两门全过即收口，不擅自扩展（不主动出高保真、不写真实后端）。
