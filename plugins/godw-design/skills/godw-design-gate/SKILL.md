# 设计工件验收门 → 登记表收敛 + gate 报告

## 输入（强制）

- 模式：`doc`（验收 `4A架构/` 全集：四文档+detail.json+需求追踪.md）或 `prototype`（验收 `原型系统/prototype.html`）。
- 实例路径（`design/change/<实例>/`）；另需实例根 `原始需求.md`（角色与目标来源；**开发者复现官不给**）与 `history/需求-原型输入.md`（用户类别来源）。
- 输出报告路径（调用方指定，如 `history/gate-arch-N.md`；N = history/ 已有同前缀最大号 +1，不覆盖不重置）。
- 登记表 `history/gate-registry.md`：不存在 → 本轮为首轮（建档轮）；存在 → 走收敛轮。

## 评审锚定卡（所有评委任务书统一附带——基准不换的载体）

每次派发，任务书前置附三样（从实例现文件生成）：

1. **评分锚定**：10=可直接上线 / 8=小瑕疵不碍用（=通过线）/ 5=核心受阻有绕路 / 2=核心走不通。
2. **已裁决清单**：gate-registry.md 的 backlog 项 + DECISIONS.md 中「不修/已裁决」条目——评委可挑战但提级需给理由，**不许原样重提**。
3. **核心流程清单 + 需求追踪表**：判定范围（FR/GR 清单及承载链），评委按行验链不漫游。

## 角色派生（动态评委，三源并集全覆盖）

漏一个角色 = 上线后该用户第一批发现问题。取并集：

1. `history/需求-原型输入.md`「用户类别」逐类（业务用户）；
2. `detail.json` roles 逐个（文档实际角色，与源 1 出入时以文档为准并记报告）；
3. **系统生态角色补全**：管理员、运维、审计/合规（涉数据留痕时）、外部集成方（涉对接时）——现实中必然存在的一律补派。

每类一个子智能体；超过 10 类才合并同类项（注明谁并入谁）。动态评委用 general-purpose + 任务书模板填空（见下）。

## 评委结构（固定评委走预制子智能体）

**固定专业评委**（方法论不随业务变，调插件 `agents/` 预制定义，tools 锁只读）：

| 评委 | 调用 | 职责 |
|---|---|---|
| 架构评审官 | `Agent(subagent_type='godw-design:arch-reviewer')` | 七维质量评审（业务目标达成/扩展性/耦合内聚/性能/冗余/抽象/复用） |
| 简洁审查官 | `Agent(subagent_type='godw-design:simplicity-officer')` | 反膨胀砍单（页面动作/流程节点/状态/通知/接口/正文重复六区） |
| 开发者复现官 | `Agent(subagent_type='godw-design:dev-reproducer')`（doc 模式） | 只凭文档复现系统（模块/接口/表/时序），猜=blocker |

调用时任务传入：工件绝对路径 + 锚定卡 + 动态上下文（如门2 联动的「受影响 FR/GR 链」）。

**节奏（探索期→收敛期两段）**：

- **探索期**：首轮（建档轮）全部角色全新派发全量走查；R2-R3 保留少量新鲜评委持续扫描。进入收敛期判据：**连续一轮新登记 <3 条且无新增 P0**。
- **收敛期**：只派**回归评委**（每类角色的任务书附登记表中该角色相关 open 问题，逐条验证「已修复且无回归」+ 复走核心流程）；新发现默认 backlog。**防松靠回归逐条验证，防漂靠少量新鲜扫描**——不再全员盲评（首轮实测教训：换评委=换基准，永不收敛）。

## 动态评委任务书（照抄改尖括号，不加引导语；前置锚定卡）

### A. 分类用户 · doc 模式（思维业务流走查）

> <锚定卡三样>
> 你是「<角色>」。你的目标：<该角色在原始需求.md 中的目标>。
> 这是系统的架构文档集：<4A架构/ 四文档+detail.json+需求追踪.md 绝对路径>。系统还没做出来，你用**思维业务流**验收：通读后在想象中把你的每一个业务流程完整执行一遍——<该角色相关流程清单>。每步问自己：我能找到入口吗？系统让我做这步吗？做完了怎么反馈？出错了怎么办？
> 你是真实而挑剔的用户：用不上、看不懂、没写、前后矛盾、系统不支持合理诉求的地方都要吐槽。区分两类：**文档缺陷**（写了但矛盾/含糊/漏写）与**需求缺口**（合理诉求整份文档都没安排——这类更要报，你是替未来真实用户提前发现问题）。
> 只输出以下 JSON（不要其他文字）：
> {"role":"<角色>","scores":[{"flow":"<流程名>","score":<0-10>,"blockers":["<文档缺陷具体位置和问题>"],"gaps":["<需求缺口+为什么合理>"],"suggestions":["<不阻断的建议>"]}]}

### C. 分类用户 · prototype 模式（实操原型）

> <锚定卡三样>
> 你是「<角色>」。你的目标：<该角色在原始需求.md 中的目标>。
> 这是可交互原型：<原型系统/prototype.html 绝对路径>（单文件，含全部页面/数据/跳转逻辑）。以<角色>身份实操你的每段旅程：<该角色相关旅程清单>。逐步验证：入口找得到吗？操作后有真实反馈吗？状态真的变了吗（提交后待办是否多一条）？跳转对吗？你可见/不可见的东西符合身份吗？
> 把不好用的都吐槽出来；区分**原型做错了**（blockers）、**整个设计就没安排**（gaps）、**可以更好**（suggestions）。管理员/运维角色走管理面运维面（用户管理/配置/日志/异常处理），没有对应页面本身就是一个 gap。
> 可用浏览器实操；无法实操时精读 HTML/JS 推演每条交互路径后作答，并在 suggestions 注明「推演非实操」。
> 只输出以上 JSON 格式。

### R. 回归评委附加段（收敛轮，追加在对应角色任务书末尾）

> 另附登记表中与你角色相关的 open 问题清单：<逐条>。逐条验证：已修复且无回归。已修复的从你的 blockers/gaps 排除；未修复或回归的在 blockers 注明「登记项未修复/回归」。不带历史评分入场。

## 汇总、登记表与判定（编排层自己做，不派子智能体）

1. **并行派发**（Agent 工具一次多任务书），评委互不知晓、任务书零引导（不辩护、不透露上轮分数）。
2. 收齐逐份解析（JSON 不合法返工重跑一次），更新 `history/gate-registry.md`：

```markdown
# 问题收敛登记表（<工件> · 更新于 <轮次>）
| 编号 | 类型 | 问题 | 来源角色/轮次 | 状态 |
|---|---|---|---|---|
| B-01 | blocker | <一句话> | 业务接口人 R1 | fixed(R3) / open |
| G-04 | gap(界内) | <一句话> | 社区开发者 R2 | 已吸收→GR-02(R4) / open |
| G-11 | gap(长尾) | <一句话> | 运维 R3 | backlog |
| S-02 | suggestion | <一句话> | 架构师 R1 | 吸收(R2) / 不收(理由) |
## backlog（不阻断放行，收口统一呈报）
```

3. **gap 三分流**（编排层判）：核心路径缺失且界内 → 回流（调 godw-design-start 的回流协议 v2：两腿吸收+GR 编号+DECISIONS 出处，登记表标「已吸收→GR-xx」）；锦上添花/边缘场景 → backlog；新用户群/新价值主张 → 越界（停止呈报用户）。
4. **blocker 准入**（评委任务书已定义）：阻断 = 核心流程走不通 / 数据错误 / 安全问题；其余按 gap/suggestion 报，编排层分流。升级须给理由（对照锚定卡）。
5. **判定线**：
   - 首轮 = 建档轮（不判 PASS/FAIL）。
   - 收敛轮 **PASS** = 登记表 open 状态的 blockers 与界内 gaps **清零** + 本轮新 blockers = 0（**不论哪个评委发现，含新鲜评委**——准入已保证 blocker 均为硬伤）+ 回归评委核心复走评分全 ≥8。**新鲜评委的评分不进判定**（第一印象天然苛刻），backlog 非空不影响。
6. **修订清单三轨**：blockers 修工件（按位置去重）；界内 gaps 走回流；简洁审查官确认的过度设计进砍单（砍出回归由下轮回归评委抓）；suggestions 择优（不收的记一句理由）。
7. 写报告（调用方指定路径）：

```markdown
# 门验收报告：<工件> · 第 N 轮（<模式>）
- 判定：建档轮 / PASS / FAIL（判定线：登记 open 清零 + 新 blockers=0 + 核心≥8）
- 派发：<动态角色评委 N + 回归评委 M + 新鲜评委 K + 固定评委（架构评审官/简洁审查官/开发者复现官）>
- 锚定卡版本：<评分锚定/已裁决清单条数/追踪表行数>
## 评分汇总
| 角色 | 流程/维度 | 分 | 与上轮比 |
## 登记表变动
- 修复确认：B-03(R2)→fixed、G-04 已吸收→GR-02 …
- 新登记：B-12、G-15(长尾→backlog) …
- 回归：B-03 修复引入新问题 → 重新 open
## 修订清单（三轨：blockers 修工件 / 界内 gaps 走回流 / 砍单执行）
## 子智能体原话附录（JSON 全文照录）
## 下一步
PASS → 放行下一步（并提示快照）/ FAIL → 修订→godw-design-check→重验（安全上限剩余 <M> 轮）
```

## 纪律

- **独立**：评委并行互不可见；同轮不因某低分提前终止其他走查。
- **无引导**：任务书照抄只填尖括号；锚定卡是客观数据不是辩护词。
- **照录**：评委原话全文进报告附录，不删改不润色——验收报告是证据。
- **收敛≠零问题**：登记表清零即收敛；backlog 是常态，为清空 backlog 无限加料是被简洁审查官反制的对象。
- **迭代即运维**：本技能本质是提前用 Agent 模拟真实用户做生产版本运维。
- **安全上限**：调用方约束（start 为每门 5 轮）；PASS 即收敛停；每轮报告独立成文件。
- **重验评委**：修订者可看登记表与修订清单，但重验的回归/新鲜评委**不带上轮评分、不带修订说明**（只给问题清单验证修复）。
- **修订后校验**：FAIL 轮的修订完成后，由调用方（start）调 godw-design-check，校验不过打回修订、不进评委。
